Kasi AI Commerce Agent: VPS Production Deployment & Migrations Manual

This guide outlines the exact, command-by-command steps required to stage, commit, and push updates from your local development machine, deploy and rebuild the stack on your Hostinger VPS, trace real-time log streams, and safely execute database migrations (including handling Alembic schema divergence).

🔒 1. Production Architecture Overview

Your live Hostinger VPS uses a high-security containerized network. The database container (kasi_db) runs PostgreSQL on port 5432 but has no public port exposure. It is 100% isolated inside the private Docker network (kasi-network).

Development runs on a local SQLite database, while production runs on PostgreSQL. Database schema changes must be synchronized using Alembic migration scripts.

Step 1: Git Staging, Committing & Pushing (Local Machine)

Before deploying, make sure your local changes are committed and pushed to GitHub cleanly.

1.1 Status Check

Verify which files are modified or untracked:

git status

1.2 Stage Changes

Stage your modified files for commit:

# Stage all files
git add .

# Or stage specific files
git add backend/app/services/groq_service.py

1.3 Commit with Clear Semantic Messages

Always write clear commit messages so other agents and team members can track history:

git commit -m "feat: enforce pre-payment logistics check and sync brand specs"

1.4 Push to GitHub

Push your local main branch to your origin remote:

git push origin main

Step 2: Code Pulling & Repository Synchronisation (VPS)

SSH into your Hostinger VPS and pull the latest code updates cleanly.

2.1 SSH into your VPS

ssh root@***.***.*.*
# Or using the IP address directly
ssh root@***.***.*.*

2.2 Navigate to the Backend Directory

cd ~/kasi-backend

2.3 Pull the latest updates

git pull origin main

Note: If you have local changes on the VPS that conflict with git pull, you can discard them using git reset --hard before pulling (make sure you don’t lose custom .env parameters):

# Optional: Only run if git pull returns a conflict error
git stash
git pull origin main

Step 3: Docker Stack Maintenance, Rebuilds & Recreation (VPS)

Whenever code changes, dependencies are added to requirements.txt, or environment parameters inside /root/kasi-backend/.env are updated, you must perform a force-rebuild and recreation.

3.1 The Force Rebuild Command (The Gold Standard)

Run this command inside ~/kasi-backend to apply fresh configs, build new code additions, and spin the container stack back up cleanly:

docker compose up -d --build --force-recreate

3.2 Flag Breakdown:

  • -d: Detached mode. Runs the container stack in the background.
  • --build: Recompile Dockerfiles. Tells Docker to fetch new dependencies from requirements.txt and rebuild container images.
  • --force-recreate: Purge and Recreate. Destroys the active containers and spins up new ones, guaranteeing that the fresh .env parameters are fully read and active.

Step 5: Database Migration Pipeline (VPS)

Since your production database uses PostgreSQL inside Docker, you must run migrations through the Flask container using docker compose exec.

5.1 Standard Database Upgrading

If the migrations pull cleanly and match the database state, run:

docker compose exec kasi-backend flask db upgrade

5.2 Checking Active Migration Version

To see what migration version your database is currently stamped with:

docker compose exec kasi-backend flask db current

5.3 Solving Alembic Divergence History (The “Target Database Not Up-to-Date” Error)

If Alembic returns an error stating that the target database is not up to date, it means the database schema has diverged from the migration history. You must stamp the database at the correct revision before upgrading.

Case A: You have custom migration scripts (e.g. 86d45ac4aec8 or rcwknn8bhoai)

  1. Stamp the database at the specific base revision that matches the database’s actual schema state:
    # Stamp to the base specifications schema:
docker compose exec kasi-backend flask db stamp 86d45ac4aec8
  2. Apply the remaining individual upgrades to bring the schema completely up to date:
    docker compose exec kasi-backend flask db upgrade

Case B: Bypassing divergent migration versions

If a specific migration script (e.g., rcwknn8bhoai_add_complete_vendor_journey_models.py or 73f67e5455ad_add_negotiation_fields.py) was already manually applied to the PostgreSQL database tables but Alembic’s history doesn’t know it:

  1. Stamp the database to that migration ID directly so Alembic knows it is already complete:
    docker compose exec kasi-backend flask db stamp rcwknn8bhoai
  2. Run the upgrade for any newer scripts:
    docker compose exec kasi-backend flask db upgrade

Step 6: Querying Live PostgreSQL Database Records Directly

If you ever need to inspect database rows or credits directly on the VPS:

6.1 Log in to the PostgreSQL container shell

docker exec -it kasi_db psql -U ******** -d ****************

6.2 Useful Live Queries (Remember the semicolon ; at the end):

  • List all tables:
    \dt
  • View registered merchants & Kasi credits:
    SELECT id, business_name, email, kasi_credits FROM users;
  • Update/Add credits to a merchant manually:
    UPDATE users SET kasi_credits = kasi_credits + 50 WHERE id = 5;
  • Inspect the last 5 invoices:
    SELECT reference, customer_name, total_amount, delivery_address, status FROM invoices ORDER BY created_at DESC LIMIT 5;
  • Exit the Postgres Shell:
    \q

Step 7: Automated Midnight Database Backups

Ensure that your live PostgreSQL database is backed up automatically.

7.1 Edit the System Cron

crontab -e

7.2 Append this daily midnight dump command:

0 0 * * * mkdir -p /root/db-backups && docker exec -t kasi_db pg_dump -U ******** **************** > /root/db-backups/backup_$(date +\%F).sql 2>&1

Your merchant tables will now be backed up automatically every midnight!
